# UX designer critique

## The macro problem

MFB has built a four-stage data pipeline — Source IMAP, Local mirror, Remote depot, Snapshots — and then refused to draw it anywhere. Every other competent backup product I have shipped (Time Machine, Backblaze, Veeam, Backupify, Tarsnap GUIs) treats the chain as the primary mental object the user manipulates. MFB treats it as an implementation detail and exposes only the leaves: an "Accounts" list, an admin "Backups" list, a "Restore" page, and a few buried `<details>` blocks. The user is asked to assemble the chain in their head from labels that don't agree on which link is which. That is the macro problem, and it is bigger than any individual page or any individual word.

The lexicon problem the audit fixates on is real, but it is downstream of the IA problem. Once the user can *see* the four stages and where they sit in them, "backup" stops needing to be overloaded — the UI has somewhere to put the disambiguation. Right now there is nowhere, so the word "backup" gets recruited to mean both "the thing happening when mbsync runs" (`partials/sync_panel.html` line 27, "Backed up X ago") and "the thing happening when restic runs" (`templates/admin_backup.html` line 4, `<h2>Backup Destinations</h2>`). Renaming without restructuring will only displace the confusion — the chain must become a first-class UI object. Everything else in this critique is in service of that.

## The chain visualisation must exist somewhere

Argument: **every screen the user lands on after login must let them point at where they are in Source → Local → Depot → Snapshot.** Not because the chain is interesting — it isn't, it's plumbing — but because the entire product *is* the chain. If the user can't locate themselves in it, every label is a guess. This is the UX equivalent of a transit map: nobody loves studying it, but you can't navigate the system without one on the wall.

The chain also doubles as the **honesty surface**. Each link can be in a known state (OK, stale, broken, not configured, in progress). Errors stop being "Backup failed" with no anchor; they become "the Local → Depot link broke at 03:14, here's why". Personas P2 (Marco) and P3 (Giulia) get the at-a-glance health they're starving for. Persona P5 (first hour) gets a teaching diagram for free, every page they load.

Three placement options, ordered by impact:

**Option 1 — Sticky chain header (preferred).** A 48–60px sticky bar under the page title showing four nodes with their state. Compact on every page, expands inline on Dashboard.

```
┌────────────────────────────────────────────────────────────────────────────┐
│ work@gmail.com                                                            │
├────────────────────────────────────────────────────────────────────────────┤
│  [Gmail IMAP] ──ok──> [Local copy] ──ok──> [S3 depot]  ◌ snapshots: 14    │
│   reachable           1.2 GB · 5m ago       last 02:00     oldest 90d     │
└────────────────────────────────────────────────────────────────────────────┘
```

State tokens: `ok` (green), `stale` (amber, no successful run in N intervals), `failed` (red, last run errored), `off` (grey dashed line, not configured). The dashed line is doing the heavy lifting — Marco sees at a glance "the offsite link isn't drawn solid, I never set it up".

**Option 2 — Dashboard hero card.** Same widget, full-size, on `/`. Per-account row collapsing to one line each. Becomes the first thing every user sees.

```
┌──────────────────────────────────────────────────────────────────┐
│  CHAIN HEALTH                                                    │
│                                                                  │
│  work@gmail.com  IMAP─●─Local─●─Depot─●─Snap  last full: 6h ago │
│  mom@libero.it   IMAP─●─Local─●─Depot─◌─ ?    no offsite set    │
│  archive@me.com  IMAP─⚠─Local─●─Depot─●─Snap  auth expired      │
└──────────────────────────────────────────────────────────────────┘
```

**Option 3 — Sidebar segment.** A "where am I" tree that stays expanded on the active account. Cheap to build, easy to ignore. Worst of the three.

I'd ship Option 1 + a fuller Option 2 on the dashboard. Same component, two densities.

## Per-screen critique

### Dashboard (`/`)

`dashboard.html` is a stat-card landing page that reports four numbers (Accounts, Messages, Usage, Errors) plus optional admin numbers. **It tells me totals and never tells me whether the system is healthy.** The "Errors" card lumps sync and backup errors. Storage shows local Maildir only — offsite size is invisible. "Recent Activity" shows sync jobs only — backup jobs are nowhere. The empty state at line 90 says *"Add your first email backup"* — wrong word, wrong frame, the user is about to add an *account*, not a backup.

Fixes: replace the stat grid with the chain card from Option 2. Demote totals to a small footer strip. Split the Errors card into "Sync" and "Offsite" with separate counts. Rewrite the empty state per the First-run section below. Move "Recent Activity" to a `Recent runs` panel with a `kind=sync|offsite` column.

### Accounts list (`/accounts`)

Functional table. The status pill conflates the same things the dashboard does — `sync_state` only, no offsite signal. Two accounts with the same address but different stores (failure F10 in journeys) are indistinguishable. No column tells me whether offsite is configured. The "Show All" admin toggle is fine but unlabeled when empty.

Fixes: add an **Offsite** column with the same `ok/stale/failed/off` token used in the chain widget. Add a tiny store badge next to the name when ambiguous. Replace the `New Account` button label with `Connect mailbox`. Sort default by health (broken first), not name.

### Account detail (`/accounts/{id}`)

The single most overloaded screen in the app. `account_detail.html` is 348 lines containing: stats strip, Overview, Mailbox Stats, Sync History, Ownership, Settings, Manage (admin), Offsite Backup (admin), Delete (admin). Eight collapsible sections, four of which are admin-only, and the *most important* one for the offsite story (`#section-backup`, line 309) is collapsed by default behind the label "Offsite Backup" — exactly the wording the audit flagged as buried.

The hero `sync_panel` is genuinely good (audit calls it out, I agree). But after the hero the page has no information hierarchy: it's a stack of equal-weight `<details>` blocks. The user has no way to tell that "Settings" is configuration but "Offsite Backup" is the other half of their data-protection story.

Fixes: (1) the chain widget goes immediately under the H2, replacing the current `stats-strip` (line 25). (2) Promote `#section-backup` out of `<details>` — give it the same hero treatment as the sync panel, two cards side by side. (3) Group the admin sections under a single "Admin actions" disclosure so the page reads `Hero → Chain → Stats → History → Admin` instead of nine equal blocks. (4) Rename `<summary>` "Offsite Backup" → `Off-site copy (snapshots)`. (5) The `Migrate Store` heading in `#section-manage` line 251 should read `Move to another store` — verb form, no jargon.

### Admin / Backup destinations (`/admin/backup`)

`admin_backup.html` line 4: `<h2>Backup Destinations</h2>` with line 6 helper text *"Manage offsite backup destinations for account maildir data. Each destination is a restic repository backed by S3 or a local path."* This sentence does three damaging things at once: it uses "backup" (collision), "destination" (collision), and "restic repository" (tool jargon leaking into the page header).

The page only manages depots; it has no per-account-per-depot health view. The "Accounts" column (line 37) is just a count — no link, no drill-down, no failure surface. The "Bucket / Path" column shows the literal word *"(encrypted)"* twice (lines 32–35), which is technically honest and operationally useless.

Fixes: rename page to `Off-site depots` (or `Storage targets` if we hate "depot"). Drop "restic" from user copy entirely — keep it in the field label `Repository password` only. Replace the count with a chip list of account names that link to detail. Add a *Status* column that aggregates each depot's last-attempt result across all accounts using it. Move the "Add Destination" form into a `<dialog>` rather than below the table.

### Admin / Stores (`/admin/stores`)

I didn't open this template but the inventory is enough: line 6 helper *"Stores are base directories where mailboxes and Dovecot home directories are saved."* The word "saved" is the bug — a non-admin reading this concludes the store *is* the backup. It isn't. It's the local working copy.

Fixes: rewrite to `Stores are the local disks where MFB keeps the working copy of your mail. They are not off-site backups.` Add a one-line `Off-site` column showing whether at least one account on this store has a depot configured (so admins can spot stores with no off-site coverage). Keep the orphan-cleanup affordance, it's good.

### Restore (`/restore`)

This is the screen with the worst conceptual collision. It is named "Restore" in the sidebar; the H2 is "Mail Restore" (line 4); the page is **IMAP-to-IMAP**, not snapshot-to-anywhere. Snapshot restore lives in `account_detail.html` line 312. The user who wants to recover from a depot snapshot will land here and bounce.

The form labels "Source account" (line 9) and "Destination account" (line 22) collide with "Backup destination" elsewhere. The icon `archive-restore` (line 4) reinforces the "this is the backup restore" misread.

Fixes: rename sidebar entry `Restore` → `Copy mail between accounts` (or split: see IA Option B/C below). Rename H2 to match. Change "Destination account" → "Target account". Remove `archive-restore` icon, use `arrow-right-left`. At the top of the page add a panel:

```
Looking for snapshot restore?  →  open the account · Off-site copy · Restore from snapshot
```

### Account form (`/accounts/new`)

Not opened in this pass, but the IA tells me everything. The form is the **first place P5 spends real time**. Today its primary CTA presumably says "Save" or "Create"; sidebar pages prior have called this thing a "backup". The user isn't sure if filling this form starts a backup, registers a thing, or both.

Fixes: H2 should read `Connect a mailbox`. CTA: `Connect and start first sync`. Below the form, three-line teaching paragraph: *"MFB will keep a local working copy of this mailbox. To protect it against disk loss, configure an off-site copy after the first sync completes."* Empty `Off-site` placeholder shown after creation, pre-filled link to the depot config. P5 leaves the page knowing the chain has two halves and they've done one.

## IA reorganization options

### Option A — Keep IA, fix copy and add chain widget

Smallest change. Sidebar untouched. Rename page titles and labels per the audit. Drop the chain widget into every page. Move snapshot restore button onto `/restore` as a tab so the term is at least co-located.

- **Pros:** lowest risk, no router changes, ships in one PR per template.
- **Cons:** "Backups" admin link still misleads; the buried `<details>` block on account detail is still buried. The structural problem survives the rename.

### Option B — Collapse "Backups" admin into the Account workflow

Kill the `/admin/backup` top-level link as a primary destination. Promote per-account off-site config to a peer of the sync panel on account detail. The depot list becomes a **utility page** under Admin → System → Storage targets. New users discover off-site through the account they care about, not through an admin nav item that means nothing to them at first glance.

```
Sidebar (after):
  Dashboard
  Mailboxes        (was: Accounts)
  Copy mail        (was: Restore)
  Webmail
  ── ADMIN ──
  Users
  Stores
  Storage targets  (was: Backups; demoted, lower in list)
  Groups
  System
  Audit log
```

- **Pros:** matches the actual workflow (depots are infrastructure, off-site policy is per-account). Removes the "Backups" misnomer entirely. Snapshot restore lives where the user expects it: on the account.
- **Cons:** admin who manages many depots loses a top-level overview — needs a "Depots" widget on `/settings`. Slight cost of teaching existing operators the move.

### Option C — Introduce a "Health" top-level page that owns the chain view

Add `Health` as the second sidebar entry (right after Dashboard). It owns the full chain matrix: every account × every link, with state tokens and drill-downs. Dashboard becomes a one-screen summary of Health. Account detail keeps a per-account chain widget.

```
Sidebar (after):
  Dashboard       (summary)
  Health          (chain matrix — NEW)
  Mailboxes
  Copy mail
  Webmail
  ── ADMIN ──
  ...
```

- **Pros:** Giulia (P3) finally has the "evidence pane" she needs. P2 (Marco) has a single URL to bookmark. Errors stop being Whack-A-Mole because there's a place that owns "is it all working?".
- **Cons:** another page to maintain. Risk of overlap with Dashboard if the line isn't drawn carefully.

**Recommendation:** ship B + C together. B fixes the conceptual error (off-site is per-account, not an admin section), C fixes the observability gap (no place owns "is the whole chain healthy?"). A alone is not enough — it papers over the structure.

## Microcopy guidelines (table)

| Situation | Pattern | Example | Anti-pattern |
|---|---|---|---|
| Primary CTA | Verb + object, sentence case | `Connect a mailbox`, `Restore from snapshot`, `Move to another store` | `Add`, `Submit`, `OK` |
| Page H2 | Noun phrase, sentence case, no icons in copy | `Mailboxes`, `Off-site depots`, `Audit log` | `Backup Destinations` (Title Case + jargon) |
| Empty state | One sentence of *what*, one sentence of *why*, one CTA | "No depots configured. Off-site depots store encrypted snapshots of your local copy. **Add a depot →**" | `No backup destinations configured yet.` (the audit's evidence) |
| Error | Which link broke, what the user can do, no stack trace | `Sync failed: Gmail rejected the OAuth token. Sign in again →` | `Backup failed — unknown error` (sync_panel.html:178) |
| Success after destructive action | State the new state, not the action | `Mailbox connected. First sync starting…` | `Account created` |
| Status line / pill | One word, with one optional modifier | `OK`, `Stale (3d)`, `Failed`, `Not set up` | `Backed up 5 minutes ago` (collision-prone) |
| Italian-style direct verbs | Use for primary CTAs and dangerous actions where the verb *is* the meaning | `Connect`, `Move`, `Delete`, `Restore` | Mealy-mouthed nouns: `Backup operation`, `Destination management` |
| Descriptive labels | Use for read-only data, table headers, badges | `Last successful sync`, `Schedule`, `Owner` | Verbs in label position: `Synced`, `Owned by` |
| Capitalisation | Sentence case everywhere; reserve Title Case for proper nouns (`Gmail`, `Microsoft`) | `Off-site depots` | `Off-Site Depots` |
| Placeholder text | Real example, never the word "example" | `s3.eu-central-1.amazonaws.com`, `you@gmail.com` | `Enter S3 endpoint`, `Type your email here` |
| Helper text | Address the misconception, not the spec | `Stores are local disks. They are not off-site backups.` | `Stores are base directories where mailboxes...are saved.` (current copy) |

## Patterns to standardize

These should be component-level, used everywhere, no one-offs.

1. **Status pill.** Four states only: `ok` (green dot), `stale` (amber dot, with relative time tooltip), `failed` (red dot, click for last error), `off` (grey hollow dot). Same component on dashboard, account row, chain widget, depot list. Currently the codebase has `badge-error`, `badge-syncing`, `badge-idle`, `badge-disabled`, `badge-admin`, `badge-user`, `stats-dot-syncing`, `stats-dot-error`, `stats-dot-ok` — three overlapping vocabularies. Collapse to one.
2. **Empty-state template.** Three slots: `icon`, `headline (one sentence)`, `body (one sentence with link)`, `cta (verb)`. Reuse on Dashboard, Mailboxes, Depots, Restore, Audit. Today every empty state is bespoke (`accounts.html:26`, `admin_backup.html:108`, dashboard line 90 — three different patterns).
3. **Needs-attention callout.** A boxed list of items, each with state pill + name + one-line reason + primary action. `dashboard.html` already has `attention-item` — promote this to the standard "anything needs you" component. Off-site failures must feed into it, not just sync failures.
4. **Error vs warning vs info distinction.** Today `flash_error` and `flash_success` are the only categories. We need at least: **error** (a thing failed, you need to act), **warning** (a thing is degraded, you should look), **info** (FYI), **pending** (a thing is in progress, do not act yet). Pick four colours, four icons, one component, kill the rest.
5. **Destructive-action confirm.** Standardize on the `delete-section` pattern from `account_detail.html:316` — type-the-name confirmation for any irreversible action — and use it for: delete account, delete depot, drain store, remove last owner. Today some actions use `onsubmit="return confirm(...)"` (line 50 of `admin_backup.html`), which is a browser native dialog and bypasses the design system. Consistency wins.

## Things the current-state doc gets wrong

1. **"Snapshot, Store, Maildir are clean — preserve them"** (TL;DR #3, also restated in `vocab-inventory.md`). Half-true. "Snapshot" is clean *as a word* but not as a UI affordance — the snapshot list is buried inside a `<details>` inside an account, has no top-level surface, and the audit's own honesty section flags it: "*Snapshots count — conflates restic snapshots with backup completeness*" (runtime-ops.md:419). Calling the term clean obscures that the *thing* it names is broken in the UI. The lexicon may stay; the screen needs work.

2. **"The hero panel on account detail is genuinely good"** (current-state.md:165). It is good at communicating sync state — and *only* sync state. By being good in isolation it teaches the user that account detail is "the sync page", which is exactly why the off-site section gets ignored two scrolls below. A "good" component that contributes to a bad mental model is not an unalloyed good. The hero needs a sibling — an off-site hero of equal weight — or its goodness will continue to absorb attention away from the chain's second half.

3. **"The mkdocs site has more disciplined vocabulary than the GUI"** (current-state.md:170, listed under "What's working today"). I'll grant the docs are more disciplined, but treating that as a positive is wrong: it means **the docs and the product disagree about what things are called**, and the docs lose every time because users read UI labels, not handbooks. A documented vocabulary that the product contradicts is worse than no documentation — it gives the team false comfort that "we have a glossary" while the running app teaches users a different one. Either the GUI adopts the docs' terms in this audit, or the docs need to be rewritten down to match the GUI. Pretending we can keep both is the actual debt.
