# Centralized Config Generation + Modular Components

## Problem

Dovecot and Roundcube configs are static files in the repo (`docker/dovecot/conf.d/`, `docker/roundcube/custom.php`), manually maintained and volume-mounted. Adding a new component (Tika) means more static files. Configuration is scattered across env vars, compose files, and config files.

## Solution

MFB becomes the single source of truth for all component configuration. At startup, MFB generates config files into named volumes that each component mounts at its expected path. Feature flags control which components are active.

## Architecture

### Volume Layout

One named volume per component. MFB writes, components read.

```
dovecot_confd volume:
  MFB mounts as    → /confs/dovecot
  Dovecot mounts as → /etc/dovecot/conf.d:ro

  Contents (generated by MFB):
    mfb-auth.conf
    mfb-mail.conf
    mfb-acl.conf
    mfb-fts.conf
    mfb-service.conf
    mfb-ssl.conf
    mfb-stats.conf
    mfb-lua-userdb.lua
    dovecot-acl

webmail_conf volume:
  MFB mounts as      → /confs/webmail
  Roundcube mounts as → /var/roundcube/config:ro

  Contents (generated by MFB):
    custom.php
```

### Components and Feature Flags

| Component | Flag | Default | Effect |
|-----------|------|---------|--------|
| Dovecot | always on | - | Config always generated |
| Webmail | `MAILFALLBACK_WEBMAIL_ENABLED` | `false` | Generates `custom.php`, shows Webmail link in nav |
| Tika | `MAILFALLBACK_TIKA_ENABLED` | `false` | Adds `fts_tika` directive to Dovecot FTS config |

Tika has no config volume — it's stateless. When enabled, MFB adds `fts_tika = http://tika:9998/tika/` to the Dovecot FTS config file.

### New Settings

```python
# config.py additions
tika_enabled: bool = False
tika_url: str = "http://tika:9998"
webmail_enabled: bool = False
webmail_imap_host: str = "dovecot"
webmail_imap_port: int = 31143
confs_path: str = "/confs"
```

`dovecot_enabled` is removed — Dovecot is always on.

### Config Generator Service

New file: `services/config_generator.py`

```python
def generate_all_configs(settings) -> None:
    """Called at app startup. Generates all component configs."""
    generate_dovecot_config(settings)
    if settings.webmail_enabled:
        generate_webmail_config(settings)

def generate_dovecot_config(settings) -> None:
    """Writes 9 files to {confs_path}/dovecot/"""

def generate_webmail_config(settings) -> None:
    """Writes custom.php to {confs_path}/webmail/"""

def reload_after_config_change(settings) -> None:
    """Regenerate changed config + call doveadm reload"""
```

Templates are Python f-strings (same pattern as `generate_mbsyncrc`). Each config file has a dedicated function that returns the file content as a string.

### Startup Flow

In `app.py` lifespan, before existing startup tasks:

```
1. ensure_confs_directories()     # mkdir -p /confs/dovecot, /confs/webmail
2. generate_all_configs(settings)  # write all config files
3. (existing startup: ensure_default_store, ensure_admin, etc.)
```

### Config Reload on Settings Change

When an admin changes a setting via UI/API:
1. MFB rewrites the affected config file(s) in the volume
2. For Dovecot: calls `reload_dovecot()` (existing function, doveadm HTTP API)
3. For Roundcube: no action needed (PHP reads config on each request)

### Docker Compose Changes

```yaml
volumes:
  dovecot_confd:
  webmail_conf:
  maildirs:
  maildirs2:

services:
  mailfallback:
    volumes:
      - dovecot_confd:/confs/dovecot
      - webmail_conf:/confs/webmail
      - maildirs:/data/mailboxes
      - maildirs2:/data/mailboxes2

  dovecot:
    image: dovecot/dovecot:latest-2.4
    volumes:
      - dovecot_confd:/etc/dovecot/conf.d:ro
      - maildirs:/data/mailboxes
      - maildirs2:/data/mailboxes2
    ports:
      - "31143:31143"
      - "9900:9900"
    environment:
      DOVECOT_API_KEY: ${MAILFALLBACK_DOVECOT_API_KEY:-mfb-dovecot-api-key-change-me}
    depends_on:
      db:
        condition: service_healthy
      mailfallback:
        condition: service_healthy

  roundcube:
    image: roundcube/roundcubemail:latest
    volumes:
      - webmail_conf:/var/roundcube/config:ro
    ports:
      - "8001:80"
    depends_on:
      dovecot:
        condition: service_started
    profiles:
      - webmail

  tika:
    image: apache/tika:latest
    ports:
      - "9998:9998"
    profiles:
      - tika
```

Key changes:
- `docker/dovecot/conf.d/` bind mounts replaced by `dovecot_confd` named volume
- `docker/roundcube/custom.php` bind mount replaced by `webmail_conf` named volume
- Roundcube uses `profiles: [webmail]` — only starts with `docker compose --profile webmail up`
- Tika uses `profiles: [tika]` — only starts with `docker compose --profile tika up`
- Dovecot env vars reduced — DB credentials now embedded in generated config by MFB
- Dovecot depends on MFB being healthy (configs must exist before Dovecot reads them)

### dovecot-acl Path

The `dovecot-acl` file is placed inside `conf.d/` (same volume). The generated `mfb-acl.conf` references it with absolute path:

```
acl_global_path = /etc/dovecot/conf.d/dovecot-acl
```

This works because Dovecot accepts any absolute path for `acl_global_path`.

### Tika Integration

When `MAILFALLBACK_TIKA_ENABLED=true`, the generated `mfb-fts.conf` includes:

```
fts_tika = http://tika:9998/tika/
```

This tells Dovecot's FTS engine to send attachments to Tika for text extraction during indexing. Tika is stateless — no config file needed, just the running container.

The Tika URL is configurable via `MAILFALLBACK_TIKA_URL` (default: `http://tika:9998`).

## Testing

- Unit tests for `config_generator.py`: verify each generated config contains expected values, respects feature flags
- Test Tika flag adds `fts_tika` to FTS config
- Test webmail flag generates `custom.php`
- Integration: `docker compose up` with new volumes, verify Dovecot reads generated config via `doveconf -n`

## Migration Path

1. Deploy new code — MFB generates configs at boot
2. Old bind-mounted configs are overridden by the new volume mount
3. Remove old `docker/dovecot/conf.d/` and `docker/roundcube/custom.php` from repo
4. No database migration needed
