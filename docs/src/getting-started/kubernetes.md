# Kubernetes

MailFallBack can be deployed on Kubernetes. This page provides guidance on adapting the Docker Compose setup for a Kubernetes environment.

!!! note "No official Helm chart yet"
    There is no official Helm chart at this time. The guidance below covers the key concepts for building your own manifests.

## Container Images

| Service | Image | Notes |
|---------|-------|-------|
| MFB | `ghcr.io/thekoma/mailfallback:main` | Built and pushed by CI on every merge to `main` |
| Dovecot | `dovecot/dovecot:latest-2.4` | Official Dovecot image |
| Roundcube | `roundcube/roundcubemail:latest` | Official Roundcube image |
| Tika | `apache/tika:latest` | Official Apache Tika image |
| PostgreSQL | `postgres:18-alpine` | Or use an external/managed database |

## Shared Storage

### Maildir PVC

All mail data lives under a shared path (default `/data/mailboxes`). Both the MFB pod (which writes via mbsync) and the Dovecot pod (which reads via IMAP) need access to the same data.

Options:

- **ReadWriteMany PVC** (e.g. NFS, CephFS, Longhorn RWX) - simplest approach, mount the same PVC in both pods
- **Single pod with sidecar** - run MFB and Dovecot in the same pod, sharing an `emptyDir` or a single-node PVC

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mailfallback-maildirs
spec:
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 50Gi
```

### Config Volumes

MFB generates Dovecot and Roundcube configuration at boot. In Docker Compose, these are shared via named volumes. In Kubernetes, use `emptyDir` volumes within a pod, or an initContainer approach:

```yaml
volumes:
  - name: dovecot-conf
    emptyDir: {}
  - name: webmail-conf
    emptyDir: {}
```

If MFB and Dovecot run in separate pods, use an initContainer in the Dovecot pod that calls the MFB API or a shared ConfigMap/Secret generated by a Job.

## UID Consistency

All containers run as UID 1000 (group 1000). Set the security context on your pods:

```yaml
securityContext:
  runAsUser: 1000
  runAsGroup: 1000
  fsGroup: 1000
```

This ensures file ownership is consistent across the maildir volume when multiple containers read and write.

## Example Pod Spec (MFB + Dovecot Sidecar)

Running MFB and Dovecot in the same pod avoids the RWX volume requirement:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mailfallback
spec:
  replicas: 1
  selector:
    matchLabels:
      app: mailfallback
  template:
    metadata:
      labels:
        app: mailfallback
    spec:
      securityContext:
        runAsUser: 1000
        runAsGroup: 1000
        fsGroup: 1000
      containers:
        - name: mailfallback
          image: ghcr.io/thekoma/mailfallback:main
          ports:
            - containerPort: 8000
          envFrom:
            - secretRef:
                name: mailfallback-env
          volumeMounts:
            - name: maildirs
              mountPath: /data/mailboxes
            - name: dovecot-conf
              mountPath: /confs/dovecot
            - name: webmail-conf
              mountPath: /confs/webmail

        - name: dovecot
          image: dovecot/dovecot:latest-2.4
          ports:
            - containerPort: 31143
            - containerPort: 9900
          env:
            - name: DOVEADM_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: mailfallback-env
                  key: MAILFALLBACK_DOVECOT_API_KEY
          volumeMounts:
            - name: maildirs
              mountPath: /data/mailboxes
            - name: dovecot-conf
              mountPath: /etc/dovecot/conf.d
              readOnly: true

      volumes:
        - name: maildirs
          persistentVolumeClaim:
            claimName: mailfallback-maildirs
        - name: dovecot-conf
          emptyDir: {}
        - name: webmail-conf
          emptyDir: {}
```

## Database

Use a managed PostgreSQL service (e.g. CloudNativePG, Amazon RDS, Google Cloud SQL) or deploy PostgreSQL in-cluster. Set `MAILFALLBACK_DATABASE_URL` in the MFB secret to point to your database.

## Health Checks

Configure liveness and readiness probes:

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8000
  initialDelaySeconds: 10
  periodSeconds: 10
readinessProbe:
  httpGet:
    path: /readyz
    port: 8000
  initialDelaySeconds: 5
  periodSeconds: 5
```

## Services

Expose MFB and Dovecot through Kubernetes Services:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: mailfallback
spec:
  selector:
    app: mailfallback
  ports:
    - name: http
      port: 8000
      targetPort: 8000
    - name: imap
      port: 143
      targetPort: 31143
    - name: dovecot-metrics
      port: 9900
      targetPort: 9900
```

## Monitoring

Dovecot exposes Prometheus metrics on port 9900. MFB exposes metrics at `/metrics` (protected by `MAILFALLBACK_METRICS_API_KEY`). Create ServiceMonitor resources if using the Prometheus Operator:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: mailfallback
spec:
  selector:
    matchLabels:
      app: mailfallback
  endpoints:
    - port: http
      path: /metrics
      bearerTokenSecret:
        name: mailfallback-env
        key: MAILFALLBACK_METRICS_API_KEY
    - port: dovecot-metrics
      path: /metrics
```
